# NFR-002 — Operational Availability Measurement

## Purpose and current architecture

The Railway Reservation System is currently a standalone, single-user C++ console application. It is not a continuously hosted server and has no always-on endpoint to monitor. Therefore, a 24/7 service-uptime claim would not describe the deployed system.

This change provides a repeatable **sampled application-startup availability check**. It does not, by itself, prove the SRS target of 99.5% operational availability.

## Proposed operating-period interpretation (approval required)

Proposed operating period: scheduled demonstration/usage windows agreed by the team and mentor. Planned maintenance and periods outside those agreed windows are excluded.

A probe is successful only when the executable launches within the configured timeout, displays the main-menu prompt (Enter choice:), accepts the normal Exit menu input, and exits with return code 0 and the expected exit message.

The monitor records UTC start/end timestamps, elapsed milliseconds, process exit code, and a reason for each success/failure in a CSV file.

**The team/mentor must approve this operating-period interpretation before Jira RRS-55 can be accepted as meeting the SRS requirement.** If 24/7 availability is required, the architecture must change to provide a continuously running service and independent monitoring.

## Running the monitor

Build the application first using the repository CMake instructions. Run the monitor from the repository root so relative data paths resolve.

Windows PowerShell:

    python monitoring/availability_monitor.py --app build/Release/railway.exe --checks 60 --interval-seconds 60 --timeout-seconds 10 --output evidence/availability-evidence.csv

Ubuntu / Linux:

    python3 monitoring/availability_monitor.py --app build/railway --checks 60 --interval-seconds 60 --timeout-seconds 10 --output evidence/availability-evidence.csv

Adjust the executable path to the actual CMake output. Keep the CSV generated by the real observation window as evidence; do not fabricate or backdate rows.

## Calculation

The script reports probe success rate:

    successful probes / total probes * 100

This is a sampled estimate of launch/menu responsiveness at probe times. It is not a continuous time-weighted uptime calculation and cannot detect failures that begin and end between probes. For a true time-based availability calculation, record the start and end of every observed outage and calculate:

    (observed operating time - observed downtime) / observed operating time * 100

## Acceptance evidence still required

- Written team/mentor approval of the operating period and measurement interpretation.
- A timestamped CSV from the agreed observation window.
- Review of failed probes and any observed downtime.
- Calculation using the approved measurement method.
- Jira RRS-55 closure only after evidence supports the stated target.

## Current evidence status

No new availability percentage is claimed by this document. Earlier successful startup and functional-test runs are regression evidence, not an uptime observation period. The 99.5% target remains unverified until approval and observation are completed.
